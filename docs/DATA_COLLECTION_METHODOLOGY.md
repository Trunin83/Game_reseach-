# Методология формирования исследовательской базы Steam

> Версия 1.0 · 22.11.2026. **Историческая реконструкция по ячейкам ноутбука** `Attestation - Trunin(1).ipynb` и предоставленным результатам. Здесь описан выполненный процесс; улучшения выделены отдельно. Не является доказательством возможности «запустить всё заново одним кликом».

## 1. Источники и границы сбора

Исходный поставщик CSV указан в ноутбуке как [The Game Census](https://thegamecensus.com/data). Получены четыре файла:

| Файл `data/raw` | Назначение | Ключевые поля |
|---|---|---|
| `games-index.csv` | Общий каталог приложений | `app_id`, `name`, `slug`, `release_date`, `is_free`, `total_positive`, `total_negative`, `health_tier` |
| `ccu-daily-top2000.csv` | Ежедневный максимум одновременных игроков | `app_id`, `date`, `max_players` |
| `health-tiers.csv` | Состояние/активность приложений | `app_id`, `slug`, `tier`, `current_players` |
| `sales-calibration.csv` | Калибровочная выборка продаж | `app_id`, `units`, `reviews` и дополнительные поля |

В ноутбуке есть ссылка на страницу загрузки, **но не сохранена надёжно проверяемая дата скачивания, лицензия и версия файлов**. Они должны быть заполнены после проверки оригинального источника. Исходная совокупность `games` существенно шире целевой аналитической выборки.

В срезе наблюдений из предоставленных материалов — **06.08–12.11.2026**, **99 дат**; временной ряд `ccu_daily` содержит **189 405** записей на **2 000** игр. Точный внешний метод формирования «top2000» не доказан одним названием файла и должен быть выяснен у поставщика.

## 2. Формирование исследовательской выборки

Фактическая логика в ячейке 101 ноутбука:

```python
all_game_ids = ccu['app_id'].dropna().astype(int).unique().tolist()
```

Таким образом, основная совокупность строится из `app_id`, встречающихся в файле CCU. Затем вычисляется множество `app_id`, которых ещё нет в `steam_app_details`, и загружаются только отсутствующие.

**Проверенное покрытие (после дозагрузки):** `steam_app_details` — 2 000 / 2 000; `games`, `health`, активность — 2 000 / 2 000; жанры — 1 990; категории — 1 997; продажи — 358. Покрытие означает наличие хотя бы одной связанной строки, а не полноту содержания.

## 3. Перенос четырёх CSV в DuckDB

В ячейках 52–55 показана последовательность: создание `data/database`, открытие `steam_analytics.duckdb`, загрузка CSV в pandas, регистрация DataFrame в текущем соединении (`con.register`), затем четыре команды `CREATE OR REPLACE TABLE ... AS SELECT * FROM df_*`.

| pandas DataFrame | Зарегистрированный источник | Физическая таблица |
|---|---|---|
| `games` | `df_games` | `games` |
| `ccu` | `df_ccu` | `ccu_daily` |
| `health` | `df_health` | `health` |
| `sales` | `df_sales` | `sales` |

**Предупреждение:** `CREATE OR REPLACE TABLE` заменяет существующую таблицу и потому является потенциально разрушительной операцией. При обновлении не запускать ячейку без резервной копии и контроля источников. `con.register()` создаёт временное отображение DataFrame, а не постоянную таблицу.

## 4. Обращение к Steam Store API

**Реальный endpoint из ячеек 48, 69, 107:**

```text
GET https://store.steampowered.com/api/appdetails
Query: appids=<app_id>&l=english&cc=us
```

- `appids` — числовой идентификатор приложения.
- `l=english` — язык ответа; `cc=us` — региональный контекст США.
- Пилотная проверка выполнялась для `app_id=730` (Counter-Strike 2), далее для первых десяти игр и затем для оставшейся выборки.
- Функция `get_steam_game()` (ячейка 69) использует `requests.Session`, `timeout=20`, глобальный `last_request_time` и **минимальный интервал 1 секунда между началами запросов**.
- `max_retries=3` означает **до трёх попыток всего**, а не три повтора дополнительно к первому запросу.
- При HTTP 429 используется `Retry-After`: числовое количество секунд либо HTTP-дата; если заголовок не удаётся разобрать — 10 секунд. После ожидания попытка считается израсходованной.
- Для других сетевых/HTTP-ошибок (`requests.RequestException`) применяется задержка `2 ** attempt` между попытками.
- После `response.json()` проверяется словарь под ключом `str(app_id)` и флаг `success`. При отсутствии данных функция возвращает `None`.
- Код **не гарантирует фиксированный лимит со стороны Steam** и не содержит внешнего журнала всех HTTP-ответов. Значение 1 секунда — фактическое ограничение клиентского загрузчика, а не официально подтверждённая квота Steam API.

Во время ручной ревизии 64 игр (ячейка 107) использовался отдельный цикл с `time.sleep(1.5)` и классификацией `success`, `not_found`, `rate_limited`, `http_<status>`, `error`.

## 5. Нормализация метаданных и транзакционная запись

Функция `save_steam_game(app_id, details)` (ячейка 91) выполняет:

1. Валидацию `app_id`, непустого словаря `details` и наличия названия от API.
2. Проверку наличия `app_id` в `games`.
3. Сравнение `csv_name` и `api_name` с нормализацией регистра и пробелов **только для уведомления** — разные названия не блокируют запись.
4. Определение `final_name` преимущественно из API; явно зафиксировано исключение `app_id=1178490` → `ParanormalHK`.
5. Начало транзакции `BEGIN TRANSACTION`.
6. `INSERT ... ON CONFLICT (app_id) DO UPDATE` в `steam_app_details`; жанры и категории также сохраняются в JSON-строках с `ensure_ascii=False`.
7. Удаление старых отношений конкретной игры из `steam_app_genres`/`steam_app_categories` и загрузку текущих массивов `genres` / `categories` по одной строке на элемент.
8. `COMMIT` при успехе, `ROLLBACK` при ошибке.

Гранулярность: `steam_app_details` — одна строка на `app_id`, `steam_app_genres` — на (`app_id`, `genre_id`), `steam_app_categories` — на (`app_id`, `category_id`). Точная действующая DDL, а не экспериментальная первоначальная схема, определяется экспортом `DATABASE_PROFILE.md`.

## 6. Основной загрузчик и дозагрузка

В ячейках 101–103 основная выборка строится по CCU, а списки `loaded`, `failed`, `skipped` фиксируют статусы **текущего запуска**. Перед запросом загрузчик проверяет наличие записи в `steam_app_details` и пропускает уже загруженные игры. Периодически печатается прогресс каждые 10 приложений.

Исторически после частичного заполнения в `steam_app_details` было 1 936 приложений. Ячейки 106–109 сформировали список **64 недостающих** и таблицы `steam_missing_games_review.xlsx` / `steam_missing_games_review_final.xlsx`. В финальном файле все 64 имеют `status=success`, `decision=load`; это журнал принятого решения. Далее в ячейках 114–118 проходила дозагрузка и проверка. Итоговый экспорт метаданных показывает **2 000 строк и 2 000 уникальных `app_id`**.

Текст ноутбука также упоминает неудачные тестовые прогоны и ошибку соответствия ID/содержимого (в том числе контроль Dota 2); опыт отражает путь исправлений, не должен скрываться в научной документации.

## 7. Контроль качества и восстановление отношений

В ячейках 120–132 выполняются проверки объёмов, количества уникальных идентификаторов, типов приложений, названий и наличия связей. Для игр без связей выполняется разбор JSON-полей `genres`/`categories` из `steam_app_details` и восстановление строк в таблицах отношений в общей транзакции.

**Результат пользовательской проверки покрытия:** у всех 2 000 есть записи в `games`, `health`, `ccu_daily`; у 10 нет строк жанров, у 3 — категорий; для 1 642 нет пересечения с `sales`. Отсутствие строк в жанрах/категориях требует проверки исходного API, но не означает автоматически дефект сохранения: массив мог быть пустым.

## 8. Аналитические преобразования

- `vw_game_activity` — `AVG(max_players)`, `MEDIAN(max_players)`, `MAX(max_players)`, число дат по `app_id`.
- `steam_games_analytics` — `peak_ccu`, `avg_daily_peak`, `min_daily_peak`, `days_observed`, `total_days`, `coverage_pct`, число жанров и категорий; по `app_id`.
- `steam_games_ranking.csv` — `rank_peak`, `rank_avg_daily_peak` и `rank_stable`; последний только при `coverage_pct >= 90`.
- Жанровые/категориальные таблицы — частоты одиночных признаков, совместные встречи, популярность сочетаний и Lift.
- Жанровые Lift-пары для основной визуализации отбираются при `genre_1_count >= 20`, `genre_2_count >= 20`, `games_count >= 20`.
- **Нельзя интерпретировать** `AVG(max_players)` как среднее число одновременных игроков за произвольный момент суток: в источнике только дневные максимумы.

См. `DATA_DICTIONARY.md` и `DATA_LINEAGE.md` для формул и файла каждого результата.

## 9. Как воспроизводить безопасно (рекомендуемый порядок)

1. Зафиксировать контрольные суммы исходных CSV, дату их получения, окно CCU, версии Python/пакетов и копию текущего файла БД.
2. Сначала выполнять **только диагностические SELECT** через `project_config.py` в read-only режиме, если в ядре нет других несовместимых соединений.
3. На отдельной копии БД воспроизвести импорт исходных CSV и создание схемы.
4. Запросы к Steam API запускать отдельно от импорта; соблюдать действующие правила доступа провайдера, вести журнал кодов ответов, среза и попыток.
5. Сверить множество `app_id` между основной выборкой и `steam_app_details`, ключи связующих таблиц, пропуски описаний и типов приложений.
6. Создать VIEW, CSV и рисунки из зафиксированной версии источников; проверить количество строк, период и суммы.
7. Избегать запуска всех ячеек экспериментального ноутбука подряд: там имеются `CREATE OR REPLACE TABLE`, `DELETE` и `UPDATE`.

## 10. Улучшения следующей версии — **не реализовано историческим кодом**

- Перенести загрузку из ноутбука в тестируемые функции `src/`, отделить REST-клиент, сохранение БД и расчёты.
- Вести `ingestion_run` / `ingestion_event`: время, источник, `app_id`, HTTP-код, попытка, хеш ответа, статус обработки, версия кода.
- Создать неизменяемый локальный snapshot входных файлов и манифест SHA-256; документировать источник и лицензию.
- Формализовать правила исключений имен и приоритетов источников в таблице/конфигурации, а не внутри `if`.
- При обновлении не заменять исходные таблицы автоматически; сначала выполнять проверку качества в staging.
- Разделить статус «API не дал значение», «пустой массив» и «ошибка загрузки»; хранить timestamp успешного получения метаданных.
